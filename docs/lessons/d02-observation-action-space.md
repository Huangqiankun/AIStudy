## 1. 建立概念：环境里存在，不等于 Agent 能看到或改变

**本课只回答**：观察空间与动作空间怎样决定 Agent 和外部世界的能力边界？

**Android / HarmonyOS 类比**：把 Agent 想成一个受权限约束的 Activity 或 Ability。

- 设备里明明有通讯录，不代表当前应用能读到；`ContentProvider`、权限和查询接口共同限定它可获得的观察。
- 系统里明明能发短信，不代表当前应用能执行；声明、授权并暴露给它的接口限定可选动作。
- Intent 里只有一个文件 URI，不等于文件内容已经进入当前页面状态；同理，用户把 PDF 路径告诉模型，不等于 PDF 正文已经进入本轮上下文。

类比边界：普通应用代码常按确定分支执行；LLM 在允许的动作中做概率性选择，可能不调用、调用错或传错参数。

```text
Environment（PDF、网页、数据库、真实系统状态）
        │  观察通道返回结果
        ▼
Harness ──把本次观察装入上下文──> Model
        <──Model 选择允许的动作────┘
        │  动作接口实际执行
        ▼
Environment 产生新结果或状态变化
```

**最小概念**：

- **观察空间**：在当前 Harness 和权限下，Agent 有可能获得的环境信息集合。
- **动作空间**：在当前 Harness 和权限下，Agent 有可能发出的操作集合。
- **上下文**：某一次模型调用实际收到的信息快照，只是观察空间中已经被取得并装入的部分。
- **工具**：观察和行动共用的接口载体；例如 `parse_pdf` 发起“读取”动作，它的返回值成为新的观察。

**确认问题**：用户只把 PDF 路径发给 Agent，但这次请求没有提供 `parse_pdf` 或其他读文件接口。此时模型“看见了什么”，又“没有看见什么”？为什么？先等学员回答，再继续。

**学员回答**：看见用户给的文件路径字符串，看不见具体文件内容。判断正确。进一步校准：路径字符串已经在当前上下文中；PDF 正文仍在环境里。当前 Harness 没有读文件接口时，正文不属于 Agent 可取得的观察；即使接口存在，也要经过“模型选择调用 → Harness 执行 → 结果回传”，正文才会成为后续模型调用的实际观察。

**第二步回答**：学员认为提供 `parse_pdf` 后 PDF 进入了观察空间，因为 Agent 具备读取资格，即使本轮未用也可能后续调用。判断正确；需保留术语边界：PDF 正文属于“可能取得的观察”，但工具尚未调用时还没有成为实际观察，也没有进入当前上下文。

## 2. 实验前预测

- 任务：读取本地 `fixtures/pdfs/simple_expense_report.pdf`，只回答日本办公室的费用金额和币种；若未读取到文件则明确说明，禁止凭常识猜测。
- 固定条件：provider `ollama`、模型 `qwen3:8b`、单任务模式、其他参数不变。
- 基线条件：`--context-mode full`，请求携带 `parse_pdf` 等工具定义。
- 观察点：首轮请求是否含 `tools`；模型是否申请 `parse_pdf`；框架实际传入的路径及返回；下一轮请求是否含 PDF 文本；最终答案是否有对应观察作依据。
- 预测问题：仅提供文件路径与同时提供读文件工具，Agent 的可见信息边界分别是什么？不要先预测固定话术，列出可能行为并说明用什么证据区分。
- 学员预测：用户给 PDF 与任务；LLM 判断意图后加载对应 Skill、插件或工具（如 `parse_pdf`）；下一轮通过工具读取正文并返回结果；再下一轮整合结果作答；把用户输入算上至少四步。
- 讲师待校准：整体“输入 → 选择读取 → 工具结果 → 最终回答”的闭环方向正确，但本实验不是上传文件，也没有动态 Skill/插件加载。用户消息给的是本地路径；Harness 在第一次模型调用前就把固定工具定义放进请求。模型只选择是否调用。一次典型成功轨迹可拆成四个事件（用户任务、模型请求工具、Harness 执行并追加结果、模型回答），但按模型 API 调用次数通常是两轮；真实轮数仍以本次轨迹为准。
- 校准后回答：确认 `parse_pdf` 由 Harness 预先加入，LLM 负责判断是否调用它来读取 PDF 正文。补充边界：参数也由 LLM 生成，真实工具由 Harness 执行。

## 6. 单变量对照：从请求中移除工具定义

先问：**只把 `full` 改为 `no_tool_calls` 后，模型仍能看到文件路径；它还可能出现哪些表现？哪项证据才能证明它真的读过 PDF？** 等学员回答后再运行。

- 唯一计划改变：`--context-mode full` → `no_tool_calls`；任务、provider、模型和其他参数保持不变。
- 先检查干预生效：首轮请求中应没有 `tools` / `tool_choice`；不能只看最终答案。
- 可能表现：明确拒绝、根据文件名或训练知识猜测、生成看似可信答案、或采取其他文本策略；不预设哪一种必然发生。
- 学员对照前预测：最可能明确表示无法读取，因为请求连工具都不会提供。预测合理；提示中“未读取则不要猜”也支持该方向，但模型可能不遵守，因此等待实测。
- 即使答案碰巧正确，也不能证明 PDF 内容进入了观察；证据应是实际工具执行及其结果出现在后续模型请求中。
- 因采样可能让两次首轮响应本就不同，单次对照只说明本次观察，不宣称普遍因果；需要时重复运行。

**换轨迹复查**：给出“请求含 `parse_pdf`，但响应没有 `tool_calls`”后，学员正确判断动作空间中存在该工具，只是本次模型没有选择它。已能区分动作接口可用与策略实际选择。
