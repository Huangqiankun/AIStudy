## 1. 建立概念：先定位断点，再讨论责任

**本课只回答**：Agent 的最终表现异常时，怎样沿完整证据链判断故障发生在模型请求、Harness 执行、结果回传、上下文组织还是权威状态层？

**类比**：一次 Android 跨进程调用失败，不能只看界面上的 Toast 就断言“服务端算错了”；要依次核对发出的 `transact()`、Binder 服务实际执行、reply Parcel、客户端解包和权威数据状态。Agent 也一样，最终文本只是链路末端的一份输出，不会自动证明前面的请求、执行和回传。

```text
请求快照                     动态轨迹                         权威状态
system + tools + user
          |
          v
 assistant.tool_calls -> Harness 执行 -> role=tool 回传 -> assistant 最终文本
          |                    |               |                    |
       决定证据             执行证据         看见证据             表达证据
                              |
                              +------------------------------> 文件/外部系统
```

**实验全景预告**（只说明路线，不揭示结果）：

- 要完成的任务：审计两份只差一个上下文回传条件的轨迹，判断断点位于哪一层。
- 学员会亲自运行：先读取基线轨迹中的请求、工具结果与下一轮消息，再运行一个单变量对照；两次都只筛选证据字段，不修改 `vendor/`。
- 会得到的产物：控制台中的消息角色、`tool_call_id`、工具返回、下一轮请求和最终输出摘要。
- 结束时要能回答：哪些证据能证明“模型请求了”“Harness 执行了”“模型收到结果了”和“副作用真的发生了”，以及哪些结论仍不能从最终文本推出。

**确认问题**：如果本地工具日志已经打印“执行成功”，但下一轮模型请求里没有对应的 `role=tool` 消息，你会先怀疑模型能力，还是 Harness 的结果回传？只选一个，并说一句理由。

## 2. 实验前预测

- 任务与输入：复用 W2 已有真实收据，比较完整回传与缺少工具结果回传的两条轨迹。
- 固定条件：相同任务、模型、工具定义与工具本地返回；只改变下一轮请求是否包含匹配的 `role=tool` 消息。
- 观察点：顶层 `tools`、`assistant.tool_calls`、本地执行结果、下一轮 `messages`、最终输出；涉及副作用时再核对权威文件或事件。
- 预测问题：缺少 `role=tool` 时，最终回答可能出现什么变化？即使最终碰巧正确，又有哪些事实仍然没有被证明？

## 7. 理解检查：每次只问一题

1. **概念复述**：为什么最终回答不能代替模型请求、Harness 执行、结果回传和权威状态这几层证据？
2. **结果预测**：工具本地成功但下一轮缺少 `role=tool` 时，哪部分可能保持不变，哪部分最可能变化？为什么？
3. **故障定位**：若有 `role=tool` 且内容正确，但模型再次发出同一个调用，你先查哪一层？还需要什么证据区分模型误解与 Harness 重放旧请求？

<details><summary>讲师核对要点（学员回答后再展开）</summary>

1. 各层分别证明“请求、执行、看见、表达、落地”，彼此不能相互替代。
2. 本地工具返回可保持不变；下一轮请求快照首先分叉，最终回答可能变化也可能碰巧相同。
3. 先确认本轮请求确实包含正确且新鲜的工具结果，再核对调用 ID、消息顺序和请求是否为新请求；证据无误后才把重点转向模型解释。
