## 1. 概念与实验全景

**核心问题**是收窄工具候选后，怎样判断节省了多少工具定义开销，又漏掉了哪些任务所需的工具？

用 Android 隐式 Intent 类比。先查询能处理某个 Intent 的 Activity，拿到按匹配程度排列的列表。若应用只把列表前几项交给下一步选择，后续动作只能使用这份候选名单。教材离线评测用任务描述给工具目录打分，比较全量工具定义与只保留前 K 个工具定义的开销，并检查任务标注的工具是否进入名单。

```text
任务描述 → 给目录里的工具排序 → 取前 K 项 → 候选工具
                                             ├─ 与标注比对，判断是否命中
                                             └─ 汇总候选工具定义的估算 tokens
```

- **任务**　使用教材内置的十条标注任务，涵盖文件读取、数据库查询等用途。
- **运行**　用教材离线 CLI 观察全量和前 5 项，再把 K 改为 1。固定任务、主表目录和评分方式。
- **产物**　控制台策略表、逐任务命中表及 JSON；另有合成目录扩展表。
- **结束时能说明**　召回率衡量哪个阶段，缩小候选的代价如何从逐任务名单里找到。

**概念确认**　如果 Android 处理 PDF 的目标 Activity 在匹配列表里排第 4，而下一步只拿到前 3 项，能否从这 3 项里选中目标 Activity？

学员指出，截取后名单里没有第 4 项，下一步无法从中选到目标 Activity。

## 2. 实验前预测

- 固定教材内置任务、默认未补齐的主表目录、TF-IDF 及相似度计算，使用 `--offline`。
- 先说明每条任务都附有一个标注工具。请学员预测检索保留前 5 项时，是否每条任务的标注工具都会进入候选，并说理由。
- 学员预测至少漏一条，因为标注工具可能排在第 5 名之后。实测 10 条全部命中。排在第 5 名之后会漏掉这一机制判断成立，本批任务未出现该条件。

## 4. 逐段读真实输出

- 主表为 35 个工具、10 条任务、K=5。全量工具定义估算为 3,857 tokens，检索每题平均估算为 516.6 tokens，控制台显示 517。两种策略均覆盖 10 条任务的标注工具。
- 逐任务核对 `offline.benchmark.per_task` 的 `gold_tools`、`retrieved` 和 `hit`。`Summary statistics` 实际返回 4 项，`analytics_summarize` 在名单中，因此命中。学员用这条记录说明候选无需填满 K 才能命中。
- 用 `offline.benchmark.strategies` 核对总体指标。控制台的 `Schema tokens` 为格式化数值，JSON 保留原始平均值。
- 两份 JSON 根节点均只有 `config` 和 `offline`。控制台显示跳过 API 评测。`config.model` 和 `config.strategies` 记录参数，实际运行范围由结果段和控制台分支信息核对。

## 5. 追到关键源码

从实验目录分次读约 36 行，先看名单，再看评分。

1. `semantic_router.py:123–134`，`SemanticRouter.retrieve` 遍历服务器候选，合并服务器和工具相似度，做全局排序并切出前 K 项。若某个服务器的工具索引无法处理查询，参见 `_route_to_tools` 的空候选返回。
2. `benchmark.py:173–184`、`197–200`。每题用 `any` 判断标注工具是否出现在候选里，再对命中与估算 tokens 求平均。当前十条任务各标注一个工具。全量召回为该程序写定的基线口径。
3. `tool_knowledge_base.py:612–616`、`619–624` 的 token 估算。核对计算作用于工具 schema 的序列化结果。真实模型请求的总输入和计费需要实际请求及用量记录。

学员从 `scored_tools[:top_k]` 说明 K 在全局排序之后才影响候选名单，再通过 `hit` 谓词指出离线评分只检查标注工具是否进入候选。讲师逐段讲解了候选打分、命中聚合与定义开销估算。故障定位题对应教材的 `agent.py:339–350`，在线检索分支把候选定义放入实际请求的顶层 `tools`。
