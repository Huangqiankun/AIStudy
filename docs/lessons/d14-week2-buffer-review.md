## 1. 建立概念：先定位断点，再讨论责任

**本课只回答**：Agent 的最终表现异常时，怎样沿完整证据链判断故障发生在模型请求、Harness 执行、结果回传、上下文组织还是权威状态层？

**类比**：一次 Android 跨进程调用失败，不能只看界面上的 Toast 就断言“服务端算错了”；要依次核对发出的 `transact()`、Binder 服务实际执行、reply Parcel、客户端解包和权威数据状态。Agent 也一样，最终文本只是链路末端的一份输出，不会自动证明前面的请求、执行和回传。

```text
请求快照                     动态轨迹                         权威状态
system + tools + user
          |
          v
 assistant.tool_calls -> Harness 执行 -> role=tool 回传 -> assistant 最终文本
          |                    |               |                    |
       决定证据             执行证据         看见证据             表达证据
                              |
                              +------------------------------> 文件/外部系统
```

**实验全景预告**（只说明路线，不揭示结果）：

- 要完成的任务：审计正确的工具结果回传与角色错标轨迹，判断每份证据能证明哪一层。
- 学员会亲自运行：先读取基线轨迹中的请求、工具结果与下一轮消息，再运行只把结果角色从 `tool` 改成 `user` 的单变量对照；两次都只筛选历史真实收据，不修改 `vendor/`。
- 会得到的产物：控制台中的消息角色、`tool_call_id`、工具返回、下一轮请求和最终输出摘要。
- 结束时要能回答：哪些证据能证明“模型请求了”“Harness 执行了”“模型收到结果了”和“副作用真的发生了”，以及哪些结论仍不能从最终文本推出。

**确认问题**：如果本地工具日志已经打印“执行成功”，但下一轮模型请求里没有对应的 `role=tool` 消息，你会先怀疑模型能力，还是 Harness 的结果回传？只选一个，并说一句理由。

## 2. 实验前预测

- 任务与输入：复用 W2 已有真实收据，先确认工具结果是否进入实际第二轮请求，再比较正确角色与错标角色。
- 固定条件：相同任务、模型、工具调用参数与工具结果文本；对照只把结果消息的角色从 `tool` 改成 `user`。
- 观察点：顶层 `tools`、`assistant.tool_calls`、本地执行结果、下一轮 `messages`、最终输出；涉及副作用时再核对权威文件或事件。
- 预测问题：缺少正确的 `role=tool` 语义时，最终回答可能出现什么变化？即使最终碰巧正确，又有哪些事实仍然没有被证明？
- 学员原始预测：缺少工具反馈后，模型会变得不可靠，但仍可能通过猜测得到答案，也可能再次调用工具或报错；角色错标为 `user` 后，预测模型可能再次调用工具，但即使答对也不能证明错标符合协议。

## 3. 运行实验

正式实验由学员在 PowerShell 中亲自运行。讲师先核实已有收据、字段和源码锚点；课堂一次只给当前步骤的一条命令，并等待真实输出。

- 输入/读取：Day 8–13 留下的真实 JSON 收据或轨迹。
- 处理/筛选：按“请求 → 执行 → 回传 → 最终输出/权威状态”选择关键字段。
- 输出/用途：形成两条并排证据链，用于定位第一个发生分歧的位置。

**基线筛选**：学员先读取 `lesson-d08-baseline.json`，观察 `system -> user -> assistant -> tool -> assistant`、工具参数、工具结果与最终回答；随后读取证据更强的 `lesson-d09-baseline.json`，直接检查 `api_turns[1].request.messages`。

**单变量对照筛选**：学员读取 `lesson-d08-role-user.json`；该历史真实收据声明唯一变化为 `messages[3].role: tool -> user`，结果文本保持不变。

**真实证据**：学员在自己的 PowerShell 中运行三个只读筛选命令并贴回完整输出，没有重新调用模型。D9 基线第二轮实际请求角色为 `system -> user -> assistant -> tool`，`tool_call_id=call_7ln57gue`，内容为 `724 CNY / 7.24`，随后 API 返回相符的最终回答。D8 角色错标对照的实际请求角色为 `system -> user -> assistant -> user`，但最终仍返回 `724 CNY / 7.24`。

## 4. 逐段读真实轨迹

| 证据层 | 要核对的字段或状态 | 能证明什么 | 不能证明什么 | 学员解释 |
|---|---|---|---|---|
| 模型请求 | `assistant.tool_calls`、参数、调用 ID | 模型提出了调用请求 | Harness 已执行、参数可信 | 能区分请求记录与执行成功 |
| Harness 执行 | 本地工具返回、执行记录 | 执行函数返回了内容 | 返回一定成功、结果已送回模型、副作用已落地 | 指出 `results` 还可能是错误响应，需按工具契约检查 |
| 结果回传 | `api_turns[1].request.messages` 中匹配的 `role=tool` | 这次实际请求携带了结果 | 模型一定正确理解或使用它 | 最初把最终 `messages` 顺序当直接证据；经请求快照与 Parcel 类比后修正 |
| 最终输出 | `assistant.content` | 模型最后表达了什么 | 前面每层都成功、相同数值必有相同路径 | 能解释错标后答对仍不证明协议正确 |
| 权威状态 | 文件、事件、外部系统读回 | 目标副作用是否真实存在 | 模型为何做出该决定 | 沿用 Day 13 的边界，不用表达证据替代副作用证据 |

## 5. 追到关键源码

**源码锚点**：`vendor/ai-agent-book/chapter2/local_llm_serving/ollama_native.py:146-177`，当前版本已重新核实行号；课堂分四小段阅读模型请求记录、工具执行、结果追加和第二次 API 请求。

- 输入 → 处理 → 输出：用户消息与工具定义 → 首次请求、执行工具、追加结果 → 携带历史发起下一次请求。
- 第 146–158 行：`tool_calls` 来自首次模型响应，追加 `assistant_message` 只能证明模型请求，不能证明工具已执行。
- 第 160–161 行：`_execute_tool_calls()` 开始执行；仅有 `results` 仍不能断言成功，要检查返回内容、错误字段和必要的权威副作用。
- 第 163–169 行：把结果追加为 `role=tool` 只更新 `conversation_history`，不证明模型已经收到。
- 第 171–177 行：第二次调用把当前历史作为 `messages` 传入；源码证明正常路径会尝试发送，真实 `api_turns[1].request.messages` 才证明本次运行实际发送了什么。
- 学员解释：能够区分“记录请求、开始执行、追加历史、真实发出第二次请求”四个时点，并指出源码控制流不能替代运行时请求快照。

## 6. 单变量对照

- 唯一改变：`messages[3].role: tool -> user`；工具结果文本保持相同。
- 保持不变：任务、`qwen3:8b`、工具调用参数、返回的金额、汇率和时间戳。
- 对照前预测：模型可能再次调用工具；即使最终答对，也不能证明角色错标是正确协议。
- 真实轨迹与结果：模型没有再次调用工具，而是直接返回 `724 CNY / 7.24`。具体时间戳也被复述，更支持“模型读取了错标为用户数据的结果”，而不是“忽略该消息”；这仍是基于输出的一种解释，不是内部因果证明。

| 实测观察 | 解释假设 | 待验证判断 |
|---|---|---|
| 正确角色与错标角色最终都回答 724；错标响应没有 `tool_calls` 属性 | 宽松模型把普通 `user` 数据当成了工具结果使用 | 不证明角色可替代；严格 provider、其他模型或恶意用户内容可能产生不同结果 |

课堂首次用 `@($j.response.tool_calls).Count` 得到错误的 `1`。复查原始属性发现 `response` 只有 `role, content, thinking`，根本不存在 `tool_calls`；Windows PowerShell 中该空值数组表达式被误计。修正为先检查 `PSObject.Properties['tool_calls']` 是否存在，再计数，得到 `HasToolCallsProperty=False`、`CorrectedToolCallCount=0`。该插曲作为“观察工具本身也必须验证”的真实反例保留。

## 7. 理解检查：每次只问一题

1. **概念复述**：为什么最终回答不能代替模型请求、Harness 执行、结果回传和权威状态这几层证据？
2. **结果预测**：工具本地成功但下一轮缺少 `role=tool` 时，哪部分可能保持不变，哪部分最可能变化？为什么？
3. **故障定位**：若有 `role=tool` 且内容正确，但模型再次发出同一个调用，你先查哪一层？还需要什么证据区分模型误解与 Harness 重放旧请求？

<details><summary>讲师核对要点（学员回答后再展开）</summary>

1. 各层分别证明“请求、执行、看见、表达、落地”，彼此不能相互替代。
2. 本地工具返回可保持不变；下一轮请求快照首先分叉，最终回答可能变化也可能碰巧相同。
3. 先确认本轮请求确实包含正确且新鲜的工具结果，再核对调用 ID、消息顺序和请求是否为新请求；证据无误后才把重点转向模型解释。

</details>

**课堂验收**：

1. 概念复述：指出最终答案可能来自正确工具链、角色错标后读取内容或未执行工具但碰巧猜中，因此最终正确不能替代四层证据。通过。
2. 结果预测：最初对 ID 错配说“大概率正常运行”；经校准后能说明不同 provider 可能拒绝、接受、忽略或重试，并准确指出匹配 ID 只证明请求与结果的关联，不能证明真实执行。通过。
3. 故障定位：最初只说检查第二轮上下文；经请求 ID、provider 原始响应与收据绑定的换例后，能判断全新请求已带正确工具结果且原始响应仍重复调用时，应优先定位模型解释与决策。通过。
