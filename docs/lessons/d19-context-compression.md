## 1. 建立概念与实验全景

**本课只回答**：Harness 怎样减少历史上下文，同时保留后续完成任务所需的决策、约束、失败路径和来源；我们要用哪些证据判断“变短”没有变成“删坏”。

**类比**：上下文压缩类似 Android 的 `onTrimMemory` + `LruCache`。内存紧张时，不是把所有对象随便截掉一半，而是按后续用途决定：可重建的缓存直接丢、重要状态保留、体积大的原始对象换成轻量表示。类比边界是：Agent 摘要通常由 LLM 生成，是有损且可能出错的；它不像确定性的对象序列化那样天然可靠。

```text
多轮工具历史                         两次模型调用之间的 Harness
┌────────────────────────┐          ┌──────────────────────────┐
│ tool result #1：长网页 │          │ 判断是否到压缩时机       │
│ tool result #2：长网页 │──筛选───▶│ 保留任务相关事实与来源   │
│ tool result #3：噪声   │──替换───▶│ 用摘要改写旧 tool result │
│ 当前用户目标与约束     │          │ 下一轮请求使用新消息列表 │
└────────────────────────┘          └──────────────────────────┘
```

与 Day 18 的边界：状态栏通常保留原历史并**追加**算好的当前结论；压缩则把臃肿原记录**替换或删除**。两者都把“需要再次归纳的内容”变成可直接检索的知识，但对信息损失和 KV Cache 的影响不同。

**实验全景预告**（不预告结果）：

- 任务：让同一个本地 `qwen3:8b` Agent 调研同一个固定研究问题，对比 `no_compression` 与 `context_aware`。
- 会运行什么：先核对真实 CLI 和本地 provider；预测后运行基线，再只改变压缩策略运行对照。没有 `SERPER_API_KEY` 时，工具会使用教材内置 mock 搜索结果；这些内容只是实验夹具，不是现实事实。
- 观察什么：工具结果是否真的被压缩后写入消息、原始/压缩字符数、每轮 prompt token、工具调用与最终答案，以及 JSON 实际保存了哪些字段、缺少哪些请求级证据。
- 产物：控制台轨迹和 `vendor/ai-agent-book/chapter2/context-compression/results/` 下两份课堂 JSON。
- 结束后能回答：压缩发生在哪一层、缩短输入与任务完成为何必须分开验证、摘要丢失关键信息时应先追哪段证据链。

**概念确认问题**：如果状态栏的动作是“保留原历史，再追加结论”，那么上下文压缩最关键的动作是什么？

## 2. 实验前预测

- 固定任务：教材脚本内置的 OpenAI 联合创始人职业状态调研任务。
- 固定条件：本地 `qwen3:8b`、同一 mock 搜索工具、相同最大迭代数和环境变量。
- 唯一变量：`no_compression` 与 `context_aware`。
- 观察点：轨迹中写入模型下一轮请求的 tool content、字符数、prompt token、工具调用轮数、最终答案及完成状态。
- 预测问题：上下文感知压缩组的输入、额外模型调用与最终答案证据完整性可能怎样变化？哪些结果不能由一次运行直接推出？
- 学员预测：上下文感知组会把原文提炼为摘要，因此下一轮主模型 prompt 会更短；但整个任务累计 Token 不一定更少，因为生成摘要本身多了一次模型调用。实测后修正为：只有摘要确实短于原文且执行路径近似时，下一轮输入才可能更短；“原文一定长于摘要”不成立。

## 3. 运行实验

正式命令一次只给当前步骤；每条命令前先说明输入、处理、输出字段及其证据作用。讲师备课只运行了 `--help` 与 `--list-strategies`，没有代跑目标实验。

### 步骤 A：环境、CLI 与 provider 核对

学员实跑确认：工作目录正确，`qwen3:8b` 已安装，`experiment.py` 存在，`LLM_PROVIDER=ollama`、`MODEL_NAME=qwen3:8b`；CLI 列出全部六种策略。此步骤没有运行研究任务。

### 步骤 B：无压缩基线

固定使用内置 mock 搜索数据，运行 `no_compression`，最多 6 轮，输出到 `results/d19-no-compression.json`。真实结果：2 轮、1 次工具调用、`Success=True`、`Overflows=0`、15.50 秒、主循环累计 2,573 Token；第一次工具输出控制台记录为 1,431 字符，第二轮 prompt 为 907 Token。指标中的 967→1,235、127.7% 不是摘要膨胀，而是无压缩策略为正文增加标题、URL 等格式后的记录口径。

脚本末尾固定打印的 `No Compression: Expected to fail with context overflow ✓` 与本次 `Success=True / Overflows=0` 冲突，只能视为预写定性提示，不能视为实测结论。本次任务在第二轮就结束，远未接近 Harness 的 128K 演示预算，因此不能推出无压缩必然失败。

### 步骤 C：读取基线轨迹

学员用 Windows PowerShell 读取 JSON；顶层为结果数组，数组元素只有 `metrics`、`final_answer`、`timestamp`。它能证明脚本保存的汇总与答案，但没有保存逐轮 `messages`、完整工具结果、压缩正文或 HTTP 请求体，不能独立证明第二轮实际输入的逐字内容。第一次读取因数组包装而只显示 `Count / Length / Rank` 等数组属性，显式取数组元素后才确认真实字段。

### 步骤 D：上下文感知对照

只把策略改为 `context_aware`，同样使用本地 `qwen3:8b`、mock 数据、温度 0.3、最多 6 轮，输出到 `results/d19-context-aware.json`。真实结果：6 轮、6 次工具调用、`Success=False`、`Overflows=0`、64.90 秒、主循环记录 9,025 Token；首次压缩 967→416，第二轮主模型 prompt 为 600 Token；后续出现 208→597、271→698、215→417、54→487、54→621，整体 1,769→3,236、182.9%。任务在第 6 轮仍重复搜索 Greg Brockman，没有形成最终答案。

日志中六次主模型调用的 Total 为 914、1,207、1,697、2,111、1,610、1,486，合计正好 9,025；另外六次摘要调用均有独立 HTTP 200，但 `ContextCompressor` 没有把其 usage 加入主 `trajectory`。所以 9,025 只是主循环 Token，不是压缩组完整成本。

## 5. 追到关键源码

课堂实际阅读的锚点：

- `compression_strategies.py:100-131`：策略分发；窗口策略首次工具结果先保持原文。
- `compression_strategies.py:454-504`：上下文感知摘要如何把 `query`、`current_context` 与搜索内容写入压缩请求。
- `agent.py:251-345`：窗口化策略的 80% 阈值、批量选择未压缩 tool 消息、`[COMPRESSED]` 防重复标记与原位替换。
- `agent.py:450-484`：本地 `messages` 如何传给非流式 API 客户端，以及只有主循环 usage 被累计到轨迹。
- `agent.py:530-635`：压缩发生在下一轮模型调用之前；工具执行结果与压缩后写入消息的内容是两层事实。

源码链结论：`query` 与 `current_context[:1000]` 决定压缩目标；每页原文先截到 5,000 字符；`max_tokens` 只是摘要输出上限，没有“摘要必须短于原文”的验收门。工具执行后，轨迹同时保存 `result` 和 `compressed_result`；非无压缩策略把 `compressed.content` 写入 `role=tool`，再把同一 `messages` 变量交给 `chat.completions.create()`。这证明本地代码路径，但 JSON 未保存序列化后的出站 HTTP body，无法逐字复核 Ollama 最终收到的请求。

## 6. 单变量对照

课堂命令只把策略从 `no_compression` 改为 `context_aware`，其余显式配置保持一致；学员先预测再运行。配置层是单变量对照，但推理未固定 seed，第一次主模型 completion 已为 266 对 487 Token，随后执行路径分叉。因此只能报告该两次真实运行的差异，不能把 2→6 轮或成败变化建立为压缩策略的因果效应。若继续研究，应固定随机性并做多次配对重复，或增加只替换固定 tool content 的消息级探针。

## 7. 理解检查

每次只问一题，学员回答后再继续：

1. 概念复述：压缩与状态栏分别怎样改变消息列表？为什么“更短”不等于“更好”？
2. 结果预测：若摘要保留姓名却删掉日期、公司和来源，后续任务可能怎样失败？
3. 故障定位：工具执行拿到了完整原文，但下一轮模型遗漏了关键约束，应按什么顺序检查工具结果、压缩模块、下一轮请求和最终答案？

<details><summary>讲师核对要点（学员回答后再展开）</summary>

1. 状态栏多为追加显式状态；压缩会替换/删除旧历史。长度下降只证明体积变化，任务信息是否保留要另验。
2. 摘要可能形成语义不完整甚至误导性的事实；需要保留主体、时间、关系与可回溯来源。
3. 先核对完整工具结果，再核对压缩输入/输出，再核对压缩摘要是否进入下一轮实际请求，最后核对模型输出与任务完成；不能用最终答案反推中间每层都正确。

</details>

**本次检查结果**：

1. 概念复述：能说明压缩改变下一轮模型看到的表示，而不改变权威工具结果；经补充后能区分状态栏的“保留历史并追加显式状态”和压缩的“替换/删除旧历史”。通过。
2. 结果预测：能预测短原文生成长摘要时当前实现仍会写入摘要，下一轮输入与压缩调用成本上升；能区分单轮成本与后续路径影响下的完整任务成本。通过。
3. 故障定位：先定位到压缩与回传层；经缩小问题后，能按工具原始结果→压缩请求输入→摘要输出→主模型请求→最终答案检查，区分 Harness 截断与压缩模型遗漏。通过。
